# Smart Inbox Assistant

An AI first-pass triage system for a pharmacovigilance shared mailbox. It reads
incoming email and PDF attachments, works out what each message is about,
extracts the key facts with a source reference for every one, and hands the
result to a human reviewer to accept or override — so a reviewer checks the
AI's work instead of starting from a blank form.

Built for the **Clinevo Technologies — Forward Deployment / GenAI Integration
Engineer** live project assignment.

> **No real patient data is used anywhere in this project.** Every document in
> the corpus is synthetic and generated by [`data/generator`](data/generator).

## The problem

A shared mailbox receives email and PDF attachments from doctors, patients and
other sources every day. Someone reads every one by hand, decides what kind of
message it is, and pulls out the important details. It is slow and error-prone,
and it is the *first pass* — not the clinical judgement — that is automatable.

Each message is sorted into one or more of four buckets:

| Category | Plain meaning | Signals |
|---|---|---|
| **Safety Report** (ICSR) | A patient had a bad reaction to a drug | An identifiable patient, a reporter, a drug, and an adverse outcome — all four, even loosely |
| **Quality Complaint** (PQC) | Something is physically wrong with the product | Broken seal, wrong colour, contamination, damaged packaging, counterfeit |
| **Info Request** (MI) | A question about a product | Dosing, administration, interactions — with no reaction and no defect |
| **Not Relevant** | Everything else | Marketing, spam, internal admin |

Labels are **multi-label, not exclusive** — a bad reaction caused by a
defective product is legitimately both an ICSR and a PQC, and the system is
built to say so rather than forced to pick one.

## Architecture

```
Angular  ──▶  Spring Boot  ──▶  Python AI service  ──▶  Oracle
(reviewer UI)  (REST, orchestration,   (LLM / OCR /        (messages,
               queue, persistence)      extraction)         extractions,
                                                            audit log)
```

Processing is queued rather than synchronous: OCR and LLM calls take seconds to
a minute per document, so the API accepts work and returns immediately while
workers drain the queue.

| Layer | Technology | Why |
|---|---|---|
| Frontend | Angular | Reviewer queue, document viewer, editable extracted fields |
| Backend API | Spring Boot (Java) | REST, orchestration, queue, persistence |
| AI services | Python (FastAPI) | LLM and OCR work, exposed to the Java layer over REST |
| Database | Oracle (PL/SQL) | Messages, extracted records, audit log |
| AI model | Gemini (vision-capable) | Scanned/handwritten pages and image description need vision; cheap with a usable free tier |

Tech choices and their trade-offs are argued in full in the
[write-up](docs/) once written.

## Two design commitments

These shape the data model rather than sitting on top of it, so they are
decided now rather than retrofitted:

**1. Every extracted fact carries its source.** A field is never stored as a
bare value — it is stored with the document and page it came from, so a
reviewer can always answer "where did this come from?". This is an audit
requirement, not a nicety.

**2. "Unknown" beats a guess.** Any field not stated in the source is recorded
as `Not stated`, never inferred, and every field carries a confidence score. A
confident wrong answer is worse than an honest gap in this domain.

## Setup

Prerequisites: **JDK 21**, **Maven**, **Node 20+**, **Python 3.12**, and
**Docker Desktop running**.

```bash
cp .env.example .env      # then fill in mailbox + GEMINI_API_KEY (see comments in the file)
docker compose up -d oracle
```
